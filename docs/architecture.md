# 实现约定

## 数据与一致性

一套 PostgreSQL 保存 raw/extracted Memory、文本 UserProfile、实体、关系、来源关联、Embedding 配置和处理任务。各 tag 独立，客户端和 session 只属于 metadata。

`add` 使用同一事务插入 raw 与 jobs。可选幂等键在 tag 内唯一；相同 key 的 content 或 metadata 不同会返回冲突。重复相同请求返回原 ID 与当前处理状态。

提炼结果保存到任务检查点，失败重试无需重新提炼原文。后续向量化、消歧和 Profile patch 可以重做；实体和 Memory 的新 ID 按 raw ID 确定性生成。相同 tag 的完全相同提炼文本复用 Memory，并增加 raw 来源。第一版不做语义级 Memory 去重或自动删除。

Worker 不在 LLM 调用期间持有数据库事务。提交时校验租约令牌，对图、全文索引、向量、Profile 和任务状态一起提交。失败回滚整次结果写入。进程被终止时，下一 Worker 可以在租约过期后回收任务。

## 实体与关系

实体检索文本为 name + type + summary。名称不唯一；同名不能直接合并。LLM 只能从同 tag 的候选实体中选择现有 ID，输出再做引用校验。实体 summary 初次建立后保持稳定，新增证据通过关联的 Memory 保存。

关系以 tag + source + target + type 唯一。明确的结束事件把关系置为 inactive，并附加变化证据；更早写入的原文重试时不会反转较新写入的关系状态。这里使用 raw 的写入时间，尚未实现完整的事实有效期/双时间模型。

关系历史不会直接筛除 Memory；原文时间、内容中的限定与后续 benchmark 将决定是否需要进一步的时态检索。

## Profile 并发

显式编辑接受最终全文和 expected_version，原子更新成功后版本递增。不存在的 Profile 是虚拟版本 0，读取不建记录，清空内容也不重置版本。

后台基于快照生成精确文本 patch。CAS 冲突时读取最新文档：目标文本仍唯一匹配的修改可以重放，目标被修改或变得歧义则保留新内容；无重复的补充信息可追加。初始空文档被别人创建时，优先保留新文档。连续冲突会重新入队。

这是保守的文本合并，不能保证发现所有语义冲突；它不引入单独的手工覆盖区。需要用真实数据评测提炼提示词和文本冲突策略。

## 检索

Memory 路：向量候选 + PostgreSQL 全文候选 → RRF。

实体路：实体向量候选 → 每个实体有限条 Memory → 按 Memory 文本向量相关性排序并去重。

两路对独立候选再次做等权 RRF：`Σ 1 / (60 + rank)`。排序分数不是事实置信度。Reranker 只对融合后的有限候选排序，失败时完整回退，避免一份结果混用两套分数。

目前用精确向量查询，所有候选在 SQL 中按 tag 过滤。后续引入近似索引时，需评测 tag 过滤后的候选数和召回损失。
